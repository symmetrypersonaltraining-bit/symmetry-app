## ⛔ THREE RULES THIS SESSION LEARNED THE HARD WAY

**1. Updates to clients go in the GROUP CHAT. One message. Never per-client.**

`messages` with `is_group = true`, `is_broadcast = false`, `client_id = null`,
`from_id = to_id =` Dustin's auth id. **One row.**

There is also an `is_broadcast = true` path that writes one row PER CLIENT and
renders as a full-screen takeover via `ClientTakeovers.tsx`. On 14 Aug I had 29
individual rows queued before Dustin stopped me: *"Do not send this as a
broadcast message to every client individually. We've talked about this. Updates
go in the group message that goes to everybody. All updates always go to the
group chat."*

The takeover channel exists and works. It is not for updates.

**2. Verify by RUNNING the statement, not by reading the code.**

The method that found everything this session: run the real statement against the
real database inside `DO $$ ... $$` ending in `RAISE EXCEPTION`. The raise aborts
the transaction so nothing commits, and the message carries the result out.

For RLS, impersonate the client — Postgres will evaluate the real policies:

```sql
set local role authenticated;
perform set_config('request.jwt.claims',
  json_build_object('sub', <auth_user_id>, 'role','authenticated')::text, true);
```

**Verify the mechanism before trusting a result.** As Bobbie Page,
`select count(*) from clients` must return 1, not 35. If it returns 35 you are
still superuser and every "OK" is meaningless.

**3. A write that succeeds silently is as bad as one that fails silently.**

Todd Prine's run saved perfectly and he reported it as broken, because nothing
on screen changed. Both failure modes leave the person with no idea what
happened, and the silent success is worse in one way: they log it twice.

| `LogClient` cardio | `cardio_logs.source` | `client_app` | `client` |
| `schedule/actions` mark done | `workout_logs.status` | `completed` | `Done as planned` |

The bulk cancel is the one that mattered most: it recoloured Google Calendar and
closed the sheet as if it had worked, while all 4,471 appointments stayed
`scheduled`. No client had ever successfully logged cardio.

**Why they hid:** the readers tolerate values their own writers cannot produce.
`TrainerCalendar` tests `status === "cancelled"` in five places. And `source`
accepts `client` on `workout_logs`, `cardio_logs`, `daily_logs`,
`meal_adherence_logs` and `metrics` — but NOT on `scheduled_workouts`. Same
column name, one table where the obvious value is silently wrong.

**Three guard tests now cover this surface:**

- `dbWrites.test.ts` — every key is a real COLUMN
- `dbCheckConstraintValues.test.ts` — every literal is a legal VALUE
- `dbInsertsSupplyRequiredColumns.test.ts` — every REQUIRED column is present

Regenerate their fixtures after any migration touching a CHECK or a NOT NULL —
the queries are in each file's header.

**Their scanners are deliberately narrow and you must know the limits.** They
read inline object literals and follow a bare identifier back to its `const`.
Anything else is invisible. That limitation already cost one bug: `log_my_weight`
built `const patch = {...}` and the first version walked straight past it. **A
green run does not mean a table is safe.**

## MICRONUTRIENTS — THE HONEST CEILING

**Do not write "the library has full nutrient data" anywhere. It will not be
true.**

| source | foods | nutrients each |
|---|---|---|
| USDA SR Legacy | ~7,800 | **128** |
| USDA Survey (FNDDS) | ~7,700 | **65** |
| USDA Branded | ~1.9M | **13** |
| Open Food Facts | 1.35M | ~13% have any |

Branded is 13 everywhere because a US nutrition label legally lists about fifteen
things. Nobody assayed the selenium in a brand of chips. **That data does not
exist**, at USDA or anywhere. Any app showing full micros on a barcode product is
estimating.

What IS covered completely: the ~15,000 generic whole foods — which is 100% of
what Dustin's meal plans are built from.

**Three things caught by looking at real output, all of which would have shipped
garbage to 35 people:**

1. **Units.** OFF reports grams; USDA mixes G/MG/UG/IU/KCAL. Conversion is driven
   by the unit each source REPORTS, never assumed. IU is refused outright — the
   IU→mcg factor differs per vitamin.
2. **Ceilings too loose.** First cut passed breadcrumbs with 2,581mg cholesterol.
   Now set from what food actually contains; over-values become NULL, never
   clamped.
3. **All-zero maps are not measurements.** A semolina pudding arrived with twenty
   nutrients all exactly 0.0000. That is a filled-in form. An all-zero map is now
   dropped to NULL.

## THE SHIP BRIDGE

A Cowork cloud session **cannot push to GitHub**. Never re-diagnose this, never
ask Dustin to rotate a PAT over a 403.

1. commit in the sandbox
2. `git bundle create /tmp/ship.bundle <last-shipped>..main` — **must be `..main`,
   not `..HEAD`**, or the bundle carries no `refs/heads/main` and the watcher
   rejects it
3. `SendUserFile` the bundle → `device_commit_files` to
   `…\Trainer App\outbox\ship.bundle`
4. write the **full 40-char SHA** to `outbox/SHIP-NOW` — **no `.txt` extension**
5. read `outbox/SHIP-RESULT.txt`

**The stop hook will report phantom unpushed commits.** The laptop does the push,
so the sandbox's `origin/main` ref goes stale. When `SHIP-RESULT.txt` says
`OK pushed`, that is the truth. `git fetch origin main` clears it.
